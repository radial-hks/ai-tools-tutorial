# Skills 仓库深度解析

## 本章解决什么

把 `mattpocock/skills` 仓库里的 **22+ 个 Skill** 逐一讲清楚：每个 Skill 是干什么的、什么时候用它、它解决什么场景的什么问题。读完你可以按任务快速定位到对应的 Skill。

> 💡 本章侧重「每个 Skill 是什么」。想看它们怎么串联起来完成一个完整工程流程，跳到 [第 3 章](03-scenarios-workflows.md)。

## 先搞清楚两个关键概念

Matt Pocock 的 Skill 分成两种调用模式，这个区分贯穿全仓库：

| 模式 | 官方术语 | 含义 | 举例 |
| --- | --- | --- | --- |
| **用户手动调用** | User-invoked | 只有你输入 `/` 命令时才触发，Agent 不会自动用 | `/grill-me`、`/to-spec` |
| **模型自动调用** | Model-invoked | Agent 会根据当前任务**自动判断**是否需要加载这个 Skill | `diagnosing-bugs`、`tdd` |

> 💡 记住：User-invoked = 你指挥 Agent 的"控制面板"；Model-invoked = Agent 自己会翻的"参考手册"。

## Engineering（工程技能）—— 逐个详解

### 一、需求与规划类（6 个）

这类 Skill 帮你解决「Agent 开始写代码之前」的问题——对齐需求、拆解任务、规划路线。

> 💡 非代码相关的需求澄清（写文档、做计划等），用 productivity 目录下的 `/grill-me`（详见本章末尾 Productivity 速览表）。

#### 1. `/grill-with-docs` ⭐ 最重要

**调用方式：** 用户手动

**一句话：** 在写代码之前，让 Agent 先反问你一系列问题，像资深工程师一样把你的需求盘问清楚。同时自动构建项目的**统一语言（Ubiquitous Language）**，写入 `CONTEXT.md` 和 ADR（架构决策记录）。

**解决什么问题：**

| 没有它时 | 有了它时 |
| --- | --- |
| Agent 按字面理解你的需求，做出来和你想要的不一样 | Agent 通过盘问把需求挖深挖透，对齐再动手 |
| 每次都重新解释项目术语 | 术语写入 `CONTEXT.md`，跨会话复用 |
| 关键决策理由丢失 | 决策写入 ADR，后来的人知道「当时为什么这样设计」 |

**适合场景：**

- 开始一个新功能
- 接手一个你不熟悉的模块
- 任何你感觉「说不太清楚想要什么」的时刻

**运行流程：**

1. 你输入 `/grill-with-docs`
2. Agent 开始反问你关于需求的细节问题
3. 你的每个回答被记录并提炼成项目术语
4. 术语写入 `CONTEXT.md`，架构决策写入 `adr/` 目录
5. 确认无误后，Agent 才开始规划实现

> 💡 Matt Pocock 自己说这是**全仓库最强大的技巧**——建立统一语言后，Agent 对项目的理解从「每句话都要解释」变成「一个词就懂」。

#### 2. `/to-spec`

**调用方式：** 用户手动

**一句话：** 把你和 Agent 刚聊完的需求，**自动整理成一份规范文档（Spec）**，发布到 Issue Tracker（GitHub Issues / Linear / 本地文件）。

**解决什么问题：**

| 没有它时 | 有了它时 |
| --- | --- |
| 聊完需求就忘了，Agent 过两天不认账 | 聊完自动生成 Spec，成为后续开发的唯一真相来源 |
| 写 Spec 费时间 | Agent 根据对话内容自动合成 |

**适合场景：**

- 长对话后需要把结论固化
- 需要让其他人（或几天后的自己）了解「要做什么」

> ⚠️ 这个命令不开启新的盘问——它只整理**当前会话里已经聊过的内容**。如果还没聊清楚需求，先用 `/grill-with-docs`。

#### 3. `/to-tickets`

**调用方式：** 用户手动

**一句话：** 把一份 Spec（或任何计划、对话结论）**拆成一串 Tracer Bullet 工单**，每个工单声明自己的前置依赖。

**关键概念：Tracer Bullet（曳光弹）**

曳光弹是一种子弹，打出去你能看到轨迹。在软件工程里，**Tracer Bullet Ticket** 是指一个很小、能独立验证的工作单元——你做完它，就能看到一条「端到端的亮线」。

| 传统任务拆分 | Tracer Bullet 拆分 |
| --- | --- |
| "实现用户登录"（模糊、太大） | "在数据库建 users 表" → "写 /login 端点" → "前端表单提交"（每步可独立验证） |

**适合场景：**

- Spec 写好后，变成可执行的工单
- 多人协作时需要明确任务边界和依赖关系

#### 4. `/wayfinder`

**调用方式：** 用户手动

**一句话：** 当一个任务**太大、超出一次 Agent 会话能完成的范围**时，自动规划成一张「决策地图」——在 Issue Tracker 上创建一系列决策工单，一次解决一个，直到路径清晰。

**适合场景：**

- 大型重构、跨模块改动
- 你不确定「该先做什么」的复杂任务

**和 `/to-tickets` 的区别：**

| `/to-tickets` | `/wayfinder` |
| --- | --- |
| 任务已知、直接拆分 | 任务太大、先铺路再拆分 |
| 产出：可执行工单 | 产出：决策工单（解决后才知道下一步） |

#### 5. `/ask-matt`

**调用方式：** 用户手动

**一句话：** 一个路由器——你告诉它当前的情况，它告诉你该用仓库里的哪个 Skill。

**适合场景：**

- 第一次用这套 Skill，不知道从哪开始
- 遇到一个不确定类型的问题

> 💡 相当于仓库自带的「智能客服」——直接问它「我想修一个性能 bug，用哪个？」

#### 6. `/setup-matt-pocock-skills`

**调用方式：** 用户手动

**一句话：** 一次性配置——告诉这套 Skill 你用哪个 Issue Tracker（GitHub / Linear / 本地文件）、工单标签怎么写、文档放哪里。每个仓库只需要跑一次。

**适合场景：**

- 首次在项目中安装这套 Skill 后
- 切换到不同的项目管理工具后

### 二、实现与测试类（3 个）

这类 Skill 覆盖「开始写代码」到「写完验证」的过程。

#### 1. `/tdd` ⭐ 最重要

**调用方式：** 模型自动调用

**一句话：** 强制执行**红 → 绿 → 重构**循环的 TDD 纪律。每个循环写一个垂直切片：一个测试 → 最少实现 → 验证通过。

**核心规则（它会在每次循环中检查）：**

| 规则 | 含义 |
| --- | --- |
| **红在绿之前** | 先写失败的测试，再写通过测试的最少代码 |
| **一次一个切片** | 每个循环只有一个 seam、一个测试、一个最小实现 |
| **测试在接缝处** | 测试只覆盖公共接口（seam），不测内部实现细节 |
| **重构不在循环内** | 红→绿循环里不重构，重构留给 `code-review` 阶段 |

**反模式识别（它会在你犯错时提醒）：**

| 反模式 | 表现 | 为什么不好 |
| --- | --- | --- |
| 实现耦合测试 | 测试内部 mock、测私有方法 | 重构时测试全坏 |
| 同义反复测试 | `expect(add(a, b)).toBe(a + b)` | 永远通过，毫无意义 |
| 水平切片 | 先写所有测试，再写所有实现 | 测试验证的是想象的行为，不是真实行为 |

**适合场景：**

- 开发新功能
- 修 Bug（先写复现测试）
- 任何需要保证代码正确性的任务

> 💡 这是 Matt Pocock 解决「Agent 写的代码跑不通」问题的核心武器。他要求 Agent 在每个 seam（可测试的公共接口）处都跑 TDD 循环。

#### 2. `/implement`

**调用方式：** 用户手动

**一句话：** 根据 Spec 或工单列表，**逐条实现**——在约定的 seam 处自动调用 `/tdd`，完成后调用 `/code-review`。

**运行流程：**

1. 读取 Spec / 工单
2. 确定 seam 列表
3. 对每个 seam：运行 `/tdd`
4. 全部完成后：运行 `/code-review`
5. 提交代码

**适合场景：**

- Spec 和工单都准备好后，开始正式实现
- 想自动化「写代码 + 写测试 + 做审查」的完整流程

#### 3. `/prototype`

**调用方式：** 模型自动调用

**一句话：** 快速构建一个**可丢弃的原型**来回答设计问题。输出是单个可分享的 HTML 文件（适合状态/逻辑验证），或多个可切换的 UI 变体。

**适合场景：**

- 「这个交互方式行不行？」——先原型再决定
- 「两种方案哪个好？」——两个都做原型对比
- 在正式投入编码前验证技术可行性

> 💡 原型就是用来扔的。`/prototype` 不产生生产代码——它的价值在于**快速回答设计问题**。

### 三、质量与审查类（3 个）

这类 Skill 确保你产出的代码不是「能跑就行」。

#### 1. `code-review` ⭐ 最重要

**调用方式：** 模型自动调用

**一句话：** 对当前改动做**双轴审查**——两个子 Agent 并行运行：

| 审查轴 | 检查内容 |
| --- | --- |
| **Standards（标准轴）** | 代码是否符合项目编码规范？有没有 Fowler 级别的坏味道？ |
| **Spec（规范轴）** | 代码是否忠实地实现了原始 Issue / Spec 的所有要求？ |

**适合场景：**

- 每次 `/implement` 结束时自动触发
- 手动改了大量代码后
- PR 提交前的最后检查

#### 2. `diagnosing-bugs` ⭐ 最重要

**调用方式：** 模型自动调用

**一句话：** 结构化 Bug 诊断流程——分阶段、有纪律地定位和修复问题。**核心思想：先建立能复现的反馈回路，再谈诊断。**

**四个阶段：**

```text
阶段 1：构建反馈回路
  └─ 找一个能稳定复现 Bug 的 pass/fail 信号（测试、curl、脚本…）
  └─ 花最多精力在这里——回路有了，Bug 就解决了 90%

阶段 2：最小化
  └─ 去掉与 Bug 无关的代码和数据，把测试范围缩到最小

阶段 3：假设与验证
  └─ 提出假设 → 用回路验证 → 确认或排除

阶段 4：修复与回归
  └─ 修复 → 回路通过 → 加回归测试 → 关闭
```

**10 种构建反馈回路的方法（按推荐顺序）：**

1. 在能触及 Bug 的 seam 处写失败测试
2. 对运行中的开发服务器发 curl / HTTP 脚本
3. CLI 调用 + 输入 fixture + 与已知正确输出 diff
4. 无头浏览器脚本（Playwright / Puppeteer）
5. 重放已捕获的 trace（网络请求/事件日志）
6. 搭建最小化复现环境
7. 属性/模糊测试：跑 1000 次随机输入找到失败模式
8. 二分定位（`git bisect run` 自动化）
9. 差分回路：跑新旧版本的同一输入，diff 输出
10. 人机协作脚本（最后手段）

**适合场景：**

- 任何「不知道为什么坏了」的 Bug
- 性能回归
- 间歇性 Bug

> 💡 这是 Matt Pocock 方法论的精髓：「先建立反馈回路」五个字比任何调试技巧都值钱。

#### 3. `/triage`

**调用方式：** 用户手动

**一句话：** 按照一套状态机规则，对工单进行**分流（Triage）**——判断优先级、分配标签、决定下一步。

**适合场景：**

- Issue Tracker 里积压了很多未分类工单
- 团队需要统一的分流标准

### 四、设计与架构类（3 个）

这类 Skill 解决「代码越来越难改」的问题。

#### 1. `codebase-design` ⭐

**调用方式：** 模型自动调用

**一句话：** 一套**共享的模块设计词汇表和纪律**——定义了模块（module）、接口（interface）、深度（depth）、接缝（seam）、适配器（adapter）、杠杆（leverage）、局部性（locality）等概念，Agent 在设计和审查时会对照这些标准。

**为什么重要：**

普通 Agent 写代码时没有「设计感」——它只关心功能对不对，不关心模块是不是「深」（接口简单但功能多）。`codebase-design` 给了 Agent 一套可操作的设计标准。

**核心概念速查：**

| 概念 | 一句话 |
| --- | --- |
| **深度模块** | 接口简单，功能强大。调用者只需知道很少就能做很多 |
| **浅模块** | 接口复杂，功能有限。调用者要了解很多细节 |
| **接缝（Seam）** | 公共接口边界——在这里测试、替换实现，不改内部 |
| **适配器（Adapter）** | 在接缝处连接两个不同接口的代码 |

**适合场景：**

- TDD 时确定「在哪个 seam 测」
- 代码审查时评估模块设计
- 重构前理解现有模块结构

#### 2. `domain-modeling`

**调用方式：** 模型自动调用

**一句话：** 主动构建和打磨项目的**领域模型（Domain Model）**——挑战术语定义、用场景压力测试、把结论写入 `CONTEXT.md` 和 ADR。

**和 `/grill-with-docs` 的关系：**

| `/grill-with-docs` | `domain-modeling` |
| --- | --- |
| 项目开始时建立统一语言 | 开发过程中持续打磨领域模型 |
| 你主动触发 | Agent 在遇到术语模糊时自动触发 |

**适合场景：**

- 发现同一个词在不同上下文里意思不同
- 新加的模块命名和现有术语不协调
- 任何「这个词到底指什么」的时刻

#### 3. `/improve-codebase-architecture` ⭐

**调用方式：** 用户手动

**一句话：** 扫描当前代码库，**识别可以「加深」的模块**——找到那些接口太复杂或功能太零散的地方，生成一份可视化 HTML 报告。你挑选一个目标后，Agent 用 `/grill-with-docs` 风格的盘问来确认重构方向。

**运行流程：**

1. Agent 扫描代码库，分析模块结构
2. 生成 HTML 报告，列出「可以加深的模块」
3. 你选择一个目标
4. Agent 盘问你关于重构方向的问题
5. 生成重构计划

**适合场景：**

- 感觉代码越来越难改，但不知道从哪下手
- 新成员入职，想快速了解代码库的架构问题
- 定期（每几天跑一次）的架构健康检查

> ⚠️ 这是一个**扫描工具**，不是自动重构机器人。它帮你找到问题，但重构决策和方向由你定。

### 五、辅助操作类（3 个）

#### 1. `research`

**调用方式：** 模型自动调用

**一句话：** 对一个问题做**高信源调研**，结果写成带引用的 Markdown 文件放入仓库。可作为后台 Agent 运行。

**适合场景：**

- 「这个库的最新 API 是什么？」——帮你查文档
- 「X 和 Y 方案各有什么优劣？」——对比调研
- 任何需要查资料但不急着出结果的调研任务

#### 2. `resolving-merge-conflicts`

**调用方式：** 模型自动调用

**一句话：** 处理进行中的 git merge 或 rebase 冲突——逐块解决，根据每边的原始意图（而非表面文本）做决策。**绝不 `--abort`**。

**适合场景：**

- Merge / rebase 冲突太多，手动处理费时间
- 冲突涉及你不熟悉的代码区域

#### 3. `wizard`

**调用方式：** 模型自动调用

**一句话：** 生成一个**交互式 bash 向导**，引导人类完成只有人类才能做的步骤——配置基础设施、设置凭证、操作不熟悉的第三方后台、执行一次性迁移。

**为什么需要它：**

有些操作 Agent 做不了——需要登录网页、需要管理员权限、需要物理操作。`wizard` 把这些步骤变成一个有引导的终端交互流程。

**适合场景：**

- 配置 CI/CD 密钥
- 在 AWS / Vercel 等控制台创建资源
- 执行数据库迁移

## Productivity（生产力技能）—— 速览

这些 Skill 不直接参与编码，但辅助你的日常工作。

| Skill | 调用 | 一句话 | 适合场景 |
| --- | --- | --- | --- |
| `grill-me` | 手动 | 非代码需求的盘问（轻量版 `/grill-with-docs`） | 写方案、做计划 |
| `grilling` | 内部 | `/grill-me` 和 `/grill-with-docs` 调用的盘问引擎 | 不直接使用 |
| `handoff` | 手动 | 为下一个接手的人（人或 Agent）写交接文档 | 任务转交、休假交接 |
| `teach` | 手动 | 把当前会话的知识提炼成可复用的 Skill | 把一次性的好做法固化为 Skill |
| `to-questionnaire` | 手动 | 把 Spec / 需求文档转成结构化的问卷 | 需求评审、用户调研 |
| `wait-what` | 手动 | 「等等，你刚才做了什么？」——让 Agent 回顾和解释最近的改动 | Agent 做了你不理解的操作 |
| `writing-for-agents` | 手动 | 教你如何写出 Agent 容易理解的文档和指令 | 写 AGENTS.md 和 Skill 时参考 |

## 快速查找表：我有 X 问题，用哪个 Skill？

| 你的情况 | 用这个 |
| --- | --- |
| 不知道从哪开始 | `/ask-matt` |
| 说不清楚想要什么 | `/grill-with-docs`（代码）/ `/grill-me`（非代码） |
| 聊完了，需要把需求固化 | `/to-spec` |
| Spec 有了，需要拆任务 | `/to-tickets` |
| 任务太大、不知道先做什么 | `/wayfinder` |
| 开始写代码 | `/implement`（完整流程）或直接 `/tdd`（单步） |
| 想快速验证一个设计想法 | `/prototype` |
| 代码写完了，要检查质量 | `code-review`（Agent 自动触发） |
| 遇到 Bug，不知道原因 | `diagnosing-bugs`（Agent 自动触发） |
| Issue 太多，需要整理 | `/triage` |
| 代码越来越难改 | `/improve-codebase-architecture` |
| 术语混乱、模块命名不协调 | `domain-modeling`（Agent 自动触发） |
| 要查技术资料 | `research` |
| merge 冲突太多 | `resolving-merge-conflicts` |
| 要配置基础设施但不会操作 | `wizard` |
| 要交接工作 | `handoff` |

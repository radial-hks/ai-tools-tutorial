# 三件套组合工作流

**受众：** 技术人员建议精读全文；无编程基础的美术、建模、TA 同事重点读「三件套分工」和「两个团队场景」两节，理解"这套组合能干什么、什么时候该用"即可。

**核验基线：** 内容按本机实际环境与官方文档核验于 2026-09（OpenViking v0.4.x、pi-herdr-agents v2.0.x、pi + herdr）。OpenViking 与 pi-herdr-agents 迭代很快，发布前建议技术负责人复核版本号与团队部署形态。

**一句话定位：** 本期核心实战章。把前几章拼成一条完整流水线：**OpenViking（记忆）+ Pi（编排）+ herdr（并行执行）** 各司其职，串成「记忆 → 编排 → 执行 → 沉淀」的闭环——让多个 agent 共享同一份长期记忆，把一个任务拆给多个子代理并行干完，再把新经验存回记忆，下次自动召回。

**标记约定：** 沿用全手册的符号：

- 🤖 **AI 可替代**：让 Pi / 子代理帮你拆任务、取证、写文档、提交代码。
- ⚠️ **必须由你决定**：账号、密钥、模型选型、最终效果、是否合并提交、记忆隐私边界，需要你亲自判断。
- 💡 **小提示**：补充说明、记忆口诀或可选做法。

## 三件套分工

一张表看清三个工具各自负责哪一环：

| 工具 | 在闭环里的角色 | 大白话 | 关键能力 |
| --- | --- | --- | --- |
| **OpenViking** | 记忆与沉淀 | 跨会话的长期记忆库 | 每个 prompt 前自动语义召回命中记忆；每个 turn 后自动捕获；提供 `viking_search` / `viking_read` / `viking_remember` 等原生工具让模型按需读写 |
| **Pi** | 编排与执行主体 | 编码 agent + 父会话指挥 | 父会话负责拆解任务、派发子代理、综合审查结果、最终落盘提交 |
| **herdr** | 承载并行执行 | 多 pane 终端工作区 | 把多个子代理放进独立的 pane / worktree 并行跑，父会话不阻塞，一眼看到「另一个面板在跑什么」 |

三者缺一不可的关系可以这样记：

- **没有 OpenViking**：每个子代理都是"失忆"的，父会话派活时要靠上下文口口相传，换一个会话就得从头交代。
- **没有 herdr**：Pi 只能串行干活，多视角取证、批量写文件都要排队等。
- **没有 Pi**：herdr 里只是几个各自为战的终端，没有人负责"拆活、派活、收活、合活"。

💡 **记忆口诀：** OpenViking 管"记住"，Pi 管"指挥"，herdr 管"并行"。记不住就串不动，指挥不好就乱，没有并行就慢。

## 端到端组合工作流

把一次完整任务拆成六步，构成闭环：

```text
┌─────────┐   ┌─────────┐   ┌──────────────┐   ┌──────────┐   ┌─────────┐
│ 1 召回  │ → │ 2 拆解  │ → │ 3 并行执行    │ → │ 4 综合合并 │ → │ 5 落盘  │
│ 记忆    │   │ 任务    │   │ （pane/worktree）│   │ 审查      │   │ git 提交│
└────┬────┘   └─────────┘   └──────────────┘   └──────────┘   └────┬────┘
     │                                                            │
     │  6 沉淀：新经验写入记忆，回到第 1 步                          │
     └────────────────────────────────────────────────────────────┘
```

### 第 1 步：会话启动，自动召回相关记忆（记忆）

启动 Pi 时，OpenViking 扩展自动工作，无需手动触发：

- 会话开始注入 **OpenViking profile 块**（用户画像、偏好等），并恢复 takeover 状态。
- 之后**每个 prompt** 都向 OpenViking 服务做一次语义召回，命中的记忆作为隐藏上下文注入，模型"想起来的"都是跟当前任务相关的部分。
- 需要精确取某条记忆时，模型可直接调用 `viking_search` / `viking_read`，按需读 `viking://` URI 下的完整内容。

🤖 这一步 AI 自动完成，你什么都不用做。状态栏出现 `OV ✓` 表示连接正常，`/viking` 可查看当前会话映射。

### 第 2 步：父会话拆解任务（编排）

父会话（Pi）把大任务拆成若干**有边界的独立子任务**，每个子任务交付一个明确结果。拆解原则：

- 读取证类的活派给**普通 pane** 里的子代理（只读，不碰工作区）。
- 写文件类的活，每个并行写作者派一个**独立受管 worktree**，互不踩脚。
- 有依赖的写操作保持串行；互相独立的活尽量并行。

🤖 拆解由父会话完成，但 ⚠️ **最终范围和验收标准由你确认**：派多少子代理、允许谁改哪些文件、要不要提交，都要在指令里写清楚。

### 第 3 步：并行子代理执行（执行）

父会话通过 pi-herdr-agents 的 `subagent()` 工具（或 `/subagent` 命令）一次性派出多个子代理：

```text
/subagent scout 梳理认证模块的代码结构和入口，返回关键文件与风险点
```

每个子代理是跑在 herdr 独立 pane 里的真实 Pi 进程，父会话立即返回、不阻塞；子代理干完自动把结果以 `subagent_result` 消息回传。需要隔离写作时用 `/worktree`：

```text
/worktree auth-fix 按已批准方案实现认证修复，并跑通相关测试
```

🤖 子代理并行跑，你可以在父会话继续干别的，或直接用 `herdr pane list` / `herdr pane read` 查看每个面板的实时输出。

### 第 4 步：父会话综合审查合并（审查）

所有子代理结果回传后，父会话做三件事：

1. **汇总**：把每个子代理的有界结果读进上下文。
2. **交叉验证**：多视角取证时，让不同子代理的结论互相印证；关键结论可再派一个独立 reviewer 复核（跨模型家族更独立）。
3. **合并**：把 worktree 里各写作者的产出按顺序合回，解决冲突，做最终检查。

⚠️ **父会话拥有整合权，子代理是"叶子"**：子代理只交付自己的有界结果，不改别人的文件、不自己 merge；合并和最终验证由父会话（最终由你）把关。

### 第 5 步：结果落盘，git 提交（落盘）

合并后的结果由父会话统一提交：

```bash
git status --short
git add <改动文件>
git commit -m "<清晰的主题行>"
git rev-parse HEAD
```

⚠️ **提交前必须由你确认**：改动范围、提交信息、是否 push 都按团队 Git 规范来；子代理通常不 push、不 merge。

### 第 6 步：新经验沉淀回记忆（沉淀）

任务完成后，把值得下次复用的经验写回 OpenViking，闭环合上：

- 关键结论、踩过的坑、团队约定：用 `viking_remember` 主动写入。
- 需要长期保存的文档/报告：用 `viking_add_resource` 导入为资源，供后续语义检索。
- 日常会话则由 OpenViking 在 turn 后**自动捕获**，压力超过阈值自动 commit，无需手动干预。

🤖 自动捕获无感进行；⚠️ 主动写入哪些记忆、放哪层、是否涉及隐私，由你决定。

## 场景实例一：多视角技术调研

**目标：** 在重大技术选型前，让多个视角独立取证、交叉验证，产出结构化报告。对应流程：**拆问题 → 并行取证 → 交叉验证 → 结构化报告**。

1. **拆问题（编排）**：父会话把一个选型题拆成 3–4 个子问题，例如「API 能力」「性能与成本」「迁移与生态」「安全与合规」，每个子问题一个独立侦察（scout）子代理，用普通 pane 只读取证。
2. **并行取证（执行）**：多个 scout 同时跑，各自查官方文档、源码、社区反馈，产出有界取证报告；父会话不阻塞，期间可继续整理你的约束条件。
3. **交叉验证（审查）**：父会话把几份报告并排比对，找出结论一致处与矛盾处；矛盾点再派独立 reviewer（尽量换一个模型家族）复核。
4. **结构化报告（落盘 + 沉淀）**：父会话综合成一份中文报告落盘提交，关键结论用 `viking_remember` 沉淀，报告全文用 `viking_add_resource` 入库，下次做相关选型时第 1 步就能自动召回。

💡 这也是本仓库「deep-research-campaign」技能与「orchestrate」技能的通用形态：**多视角独立取证 + 父会话交叉纠偏**。

## 场景实例二：批量文档 / 代码任务

**目标：** 把一批互相独立的文件写作/改动任务并行拆出去，最后合并提交。对应流程：**拆文件 → 并行 worktree 写作 → 合并提交**。

1. **拆文件（编排）**：父会话把一批文档或代码改动按文件/模块拆成 N 个独立子任务，每个写作者只允许改自己的文件。
2. **并行 worktree 写作（执行）**：每个写作者派一个独立受管 worktree（`/worktree <name> <task>`），互不共享工作区，避免冲突；父会话在同一仓库的另一 checkout 继续总览。
3. **合并提交（审查 + 落盘）**：各 worktree 产出回传后，父会话逐个检查、解决冲突、统一提交；最终 commit 由父会话（经你确认）完成。

⚠️ **关键纪律：** 并行写作者必须各占一个 worktree、各管各的文件清单；两个子代理同时改同一文件一定打架。有先后依赖的改动保持串行。

## 与前七期的衔接

这一套不是全新发明，而是前几期能力的自然合流：

| 前几期 | 贡献 | 本期补上的拼图 |
| --- | --- | --- |
| 第 1–3 期（Copilot / Skill / Hermes） | 单机编码、流程复用、任务执行与内置记忆 | 提供了"日常怎么用 AI 干活"的地基 |
| 第 4 期（Pi 工作流） | Pi 作为透明可扩展的编码 agent + herdr 并行工作区 | 本期把它升级成"父会话编排 + 子代理并行"的编排中枢 |
| 第 5 期（记忆系统） | 厘清 Agent 长期记忆该记什么、怎么选型 | 本期用 OpenViking 落地"多 agent 共享同一份长期记忆" |
| 第 6–7 期（DSH / Matt Pocock Skills） | 更多 agent 形态与工程技能库 | 提供可编排的 skill 与角色参考 |

一句话总结合流：**第 4 期给了"编排与并行"的手脚，第 5 期给了"记忆"的大脑，OpenViking 补上最后一块拼图——让并行跑起来的多个 agent 共享同一份长期记忆，而不是各自失忆。**

## 常见坑与排错

> 本节涉及快速迭代功能，核验时间：2026-09。

| 现象 | 排查方向 |
| --- | --- |
| 状态栏 `OV ✗`，召回为空 | `curl http://localhost:1933/health` 确认服务可达；检查 `~/.openviking/ovcli.conf` 的 endpoint 与 API Key |
| 派出的子代理结果没回到父会话 | 确认在 herdr 里以 `HERDR_ENV=1` 启动 Pi；结果以 `subagent_result` 回传，父会话无需轮询 session 文件 |
| 多个写作者互相覆盖 | 每个并行写作者必须各占独立受管 worktree、各管各的文件清单，禁止共享 checkout |
| 子代理"失忆"，每次都要重新交代 | 检查 OpenViking 扩展是否加载（`pi list` 应能看到 `extensions/openviking`）；确认 recall 的 `scoreThreshold` 与 `minQueryLength` 配置合理 |
| 想读 `viking://` 却报错 | 不要用本地 `read`/`bash` 去读 `viking://` URI，改调用 `viking_read` / `viking_search` 工具 |

# OpenViking 是什么

## 本章解决什么

前几期我们攒下了几块拼图：第 4 期的 **Pi**（终端里的极简编程助手）、第 5 期的 **Agent 记忆系统**（为什么 AI 需要长期记忆、三家记忆系统怎么选）。本期把这两块拼起来，讲一个更完整的方案：**OpenViking**。

本章回答三件事：

1. OpenViking 到底是什么、解决什么问题；
2. 它由哪些核心概念组成（记忆库、会话提交、分层供给、资源导入、Peer、检索）；
3. 它在第 5 期对比过的记忆系统生态里处于什么位置，为什么本期要选它和 Pi 搭配。

读完你可以判断：自己要不要在本机装一套 OpenViking，以及它和第 5 期那三家的区别。

## 一句话说清楚

**OpenViking 是开源的、专为 AI 智能体（Agent）设计的上下文数据库（Context Database）。**

用更口语的方式讲：

> **它把 Agent 需要的「记忆、资源、技能」统一组织成一棵 `viking://` 虚拟文件系统目录树；会话结束时自动把对话沉淀成记忆，下次会话自动召回、按需加载——让 Agent 跨会话、跨工具不再"失忆"。**

在官方 Pi 集成文档里，它被描述为给 Pi 提供「跨会话长期记忆」和「上下文接管（Context Takeover）」的底座。两个说法是一回事：**官方定位是"上下文数据库"，落地到编码助手上的效果是"长期记忆 + 上下文接管"。**

## 它解决什么问题：会话结束，AI 就"失忆"

这一段和第 5 期开头讲的是同一个痛点，但 OpenViking 的回答更彻底。先回忆一下：大多数 AI 工具每次开新会话都是"白纸一张"——你上周讲过的项目背景、跑通的流程、踩过的坑，换个会话就全忘了。

| 场面 | 典型例子 | 浪费在哪 |
| --- | --- | --- |
| 重复自我介绍 | "我是负责角色建模的小李，我们项目用 Maya，单位是厘米" | 每次新会话都要重新教一遍基本背景 |
| 重复讲项目背景 | "这个项目是低模风格，贴图用 PBR 流程，输出目录在 `D:/Projects/Demo/export`" | 项目约定越长，讲得越久，还容易讲漏 |
| 重复踩坑 | "上次提醒过：批量处理前必须先备份原文件" | 同一个坑换个会话又踩一遍 |

### 上下文（Context）与记忆（Memory）是两回事

要理解 OpenViking 解决什么，先分清两个词：

| | 上下文（Context） | 记忆（Memory） |
| --- | --- | --- |
| 内容 | 当前这次会话里 AI 看得到的东西 | 跨会话沉淀下来的事实、偏好、经验 |
| 生命周期 | 会话结束即失效 | 长期保存、持续更新 |
| 类比 | 工作台上摊开的图纸 | 越攒越厚的个人笔记 + 资料库 |

> 💡 官方原话点出了价值链条：**项目背景讲过了，不该换个 Session 再讲；文档读过了，不该每个 Agent 从第一页重读；一套做法已经跑通，不该下次再摸索一遍。**

OpenViking 要做的，就是让「上下文」里值得留的东西自动变成「记忆」，下次自动取回。

### 官方实证：跨工具记忆接力（2026-08-28 官方直播）

官方用两个 Python 项目做过一次现场实证：在项目 A 里告诉 Claude Code 几条开发偏好（行宽 120、用 pytest、测试文件命名 `*_spec.py`、提交信息用中文），完成任务、归档、提取记忆后，切到 **Codex** 打开项目 B，只说一句「按我平时的偏好加 lint 和测试配置」——Codex 的自动召回记录里出现了那几条偏好，生成的 Ruff / pytest 配置完全对齐；对照组里关掉 OpenViking，Codex 只能给出默认风格（行宽 88、`test_*.py`）。

这场演示也把「记忆闭环」走完整了：

1. **你开始说话** → 自动检索相关记忆，附到 prompt 后；
2. **每轮对话结束** → 自动记录进会话；
3. **会话结束** → 归档，后台蒸馏成可读的 Markdown 记忆文件；
4. **下次换任何工具** → 回到第 1 步，召回同一份记忆。

> 💡 闭环的每一步由专用集成的 hook 在后台驱动，**不依赖模型「想起来」调工具**；仅通过 MCP 接入的客户端也能读到同一份记忆，但需要模型自己找到并调用检索工具——这也是第 5 章 Copilot 插件选 hook 路线的原因。

## 核心概念

下面七个概念，是看懂后面安装和使用章节的地基。

### 1. 记忆库：一棵 `viking://` 虚拟文件树

OpenViking 没有把记忆塞进一个扁平的表里，而是把所有上下文组织成一棵**虚拟文件系统**，每个上下文都有一个唯一地址（`viking://` URI），可以用确定性的路径定位、浏览、读取。

```text
viking://
├── resources/              # 资源：项目文档、代码库、网页等
├── user/
│   └── {user_id}/          # 当前用户的私有上下文
│       ├── memories/       # 用户记忆
│       ├── resources/      # 用户私有资源
│       ├── skills/         # 用户私有技能（默认）
│       ├── peers/{peer_id}/
│       │   ├── memories/   # 某个项目的记忆
│       │   └── resources/  # 某个项目的资源
│       └── sessions/       # 会话与历史归档
└── agent/
    └── skills/             # account 全局共享技能（可选）
```

> 💡 用文件系统而不是"一大袋向量"，好处是**可浏览、可观测**：检索走了哪些目录、读了哪个文件，全程有迹可循，出错时能定位到具体哪一步。

### 2. 三种上下文类型：Resource / Memory / Skill

| 类型 | 用途 | 生命周期 | 谁在写 |
| --- | --- | --- | --- |
| **资源（Resource）** | 知识与规则（文档、代码、FAQ） | 长期、相对静态 | 用户主动添加 |
| **记忆（Memory）** | Agent 的认知（用户偏好、学到的经验） | 长期、动态更新 | Agent 自动提取 |
| **技能（Skill）** | 可调用的能力（工具、MCP、工作流） | 长期、相对静态 | 用户或系统添加 |

> 💡 一句话记住分工：**资源是"资料"，记忆是"认知"，技能是"能力"。**

### 3. 分层供给：L0 / L1 / L2

海量上下文一次性塞进提示词，又贵又吵。OpenViking 在写入时就把内容处理成三层：

| 层级 | 名称 | 默认正文上限 | 用途 |
| --- | --- | --- | --- |
| **L0** | 摘要 | 256 字符 | 向量检索、快速过滤 |
| **L1** | 概览 | 4000 字符 | 精排、内容导航 |
| **L2** | 详情 | 无统一上限 | 完整内容、按需加载 |

Agent 先看摘要定位，再看概览判断要不要深入，最后才读详情——**只加载真正需要的部分**，省 Token 也降噪。

### 4. 会话自动捕获与提交（Commit）机制

这是 OpenViking 区别于"手动记笔记"的关键：**会话会被自动捕获，提交（Commit）时自动把对话沉淀成记忆。**

- 会话进行中，用户和助手的消息（含工具调用）被持续捕获进 **会话（Session）**；
- 触发提交时，系统先把消息归档、生成摘要，再**异步**从对话里提取长期记忆；
- 提取不是照抄聊天记录，而是先向量预过滤找相似记忆，再由 LLM 做去重决策（创建 / 合并 / 跳过 / 删除），最后写入记忆库。

内置的记忆类型有 `profile`（画像）、`preferences`（偏好）、`entities`（实体）、`events`（事件）、`experiences`（经验）等，也可以按业务自定义扩展。

### 5. 资源导入

除记忆外，OpenViking 还能导入外部资料：文档、代码仓库、网页、PDF、图片、音视频等。导入后系统自动解析并生成 L0/L1 摘要，让这些资料也能被语义检索——相当于给 Agent 建一个「可搜索的团队资料库」。

### 6. Peer：项目级的记忆分区

**对等节点（Peer）** 是「把一个项目的记忆归拢在一起」的一段路径前缀：

```text
viking://user/<you>/peers/<peer_id>/memories
```

默认按 Git 仓库的 `origin` 地址派生 Peer 标识：同一个仓库的所有 clone、worktree、子目录共用同一个 Peer——**同一个项目的记忆自动归到一处，不同项目互不干扰**。不在 Git 仓库里的目录，记忆则进入用户级空间，不会为每个临时目录凭空造一个空 Peer。

### 7. 检索方式

OpenViking 提供两种检索：

| 检索 | 特点 | 适用 |
| --- | --- | --- |
| `find()` | 单一查询，直接语义搜索，低延迟 | 明确知道要找什么 |
| `search()` | 用 LLM 分析意图，生成 0–5 个查询，走目录递归检索 | 复杂任务、需要结合会话上下文 |

检索不是"平铺式全文匹配"，而是**目录递归检索**：先向量定位高分目录，再在目录内二次检索、逐层下探，最后 Rerank 精排——既找到语义匹配的片段，也保留它所在的完整语境。

## 与第 5 期 Agent 记忆系统的衔接

第 5 期横向对比了三家记忆系统（[三个记忆系统横向对比](../05-agent-memory/02-memory-systems-comparison.md)）：TencentDB Agent Memory、Mnemosyne、Hindsight。OpenViking 不在那张表里——它是**第四种路线**，可以这样对齐：

| 第 5 期三家 | 定位 | OpenViking 的对应关系 |
| --- | --- | --- |
| **TencentDB Agent Memory** | 团队记忆中枢（四类资产 + L0–L3 蒸馏） | 最接近：OpenViking 也是"上下文 / 记忆中枢"，但用**文件系统范式**替代了面板 + 三件套 |
| **Mnemosyne** | 本地轻量记忆层（一个 pip 包 + SQLite） | OpenViking 更重（要起服务），但功能面更广（资源 + 技能 + 会话 + Peer） |
| **Hindsight** | 学习型记忆引擎（Retain / Recall / Reflect） | OpenViking 的"会话 Commit → 记忆提取"是更工程化的自动沉淀，不强打"推理出新结论" |

第 5 期的结论里有一条是「Mnemosyne 是唯一对 Hermes 和 Pi 都有官方原生支持的一家」。到本期，这条结论要补一句：**OpenViking 也有官方原生 Pi 扩展**（第 2 章要装的正是它），而且它把「记忆 + 资源 + 技能 + 会话」整合进一个系统，适合想要"一套完整上下文底座"的团队。

> 💡 一句话定位：**第 5 期教你"给 AI 装记忆"，本期教你"给 AI 装一套上下文操作系统"。**

## 什么时候不需要它：官方划的三条边界

选型文档里最值钱的往往是「什么时候别用」。官方博客（见参考）划了三条硬边界：

| 边界 | 说明 |
| --- | --- |
| 已有好用的向量检索 / RAG | 官方 FAQ 同样建议：能用就继续用，不为替换而替换 |
| 无状态的一次性调用 | 每次都是 one-shot，没有可积累的东西 |
| 需要「刚说完一秒内就能从长期记忆召回」 | 记忆是会话提交后**异步**提取的；秒级应答靠的是会话内上下文，不属于长期记忆 |

## 四种运行形态

| 形态 | 适合 | 数据在哪 | 成本 |
| --- | --- | --- | --- |
| **开源自建**（AGPLv3） | 想完全掌控、愿意自己运维的个人/团队 | 你部署的地方（自选模型） | 免费；代价是服务器、模型用量和维护时间 |
| **托管·个人版** | 个人开发者，不想跑服务器 | 火山引擎北京区（豆包系模型） | 每库前 50 个文件免费，其后按时计费 |
| **托管·企业版** | 多人多 Agent、严格隔离 | 火山引擎北京区 | 按库创建起时计费 |
| **私有化部署**（BYOC / 离线） | 数据必须留在自己机房 | 自己的云账号 / VPC / 离线 | license 密钥 + 定制报价 |

> 💡 本团队走的是「开源自建」路线：服务端在内网、数据不出网。官方选型测验（12 题、约 3 分钟，含十种「agent wrangler」自画像）可用于个人评估，拿不准时先测再决定。

## 一句话总结

> OpenViking 是给 AI Agent 的**上下文数据库**：记忆、资源、技能统一成一棵 `viking://` 文件树，会话自动提交（Commit）沉淀记忆、下次自动召回，Peer 按项目隔离，L0/L1/L2 分层按需加载——让 Agent 跨会话、跨工具、跨项目"越用越懂你"。

下一章动手：在本机装好 OpenViking 服务端，并把它接入 Pi。

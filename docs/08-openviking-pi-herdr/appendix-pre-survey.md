## 二、结果怎么用（讲者分流逻辑）

| 结果信号 | 分享侧重调整 |

| ②选 A/B 的多 | 开场直接用"重复自我介绍"痛点切入，概念部分压缩 |
| ⑦选 A/B 的多 | 把 AGENTS.md 的局限（越长越读不完）讲透，再引出记忆库的分层供给 |
| ⑦选 C/D 的多 | 加大「可浏览可观测」（`viking://` 文件树、检索轨迹）篇幅，这是它区别于普通 RAG 的卖点 |

## 三、官方口径的反方观点（分享前自查）

选型博客划的三条「不需要它」的边界，分享里要主动讲出来，防止过度推销：

1. **已有好用的向量检索 / RAG** → 能用就继续用；
2. **无状态一次性调用** → 没有可积累的东西；
3. **需要"刚说完一秒内就能召回"** → 记忆是会话提交后异步提取的，秒级应答属于会话内上下文。

## 四、现场首试配方：一条偏好起步（源自官方直播）

不要现场演示"导入整个知识库"这种大动作。官方验证过的最小可信演示是**一条开发偏好的跨工具接力**：

1. 在工具 A 里用一句话声明偏好：`这个项目行宽用 120，测试用 pytest，测试文件命名 *_spec.py，提交信息用中文`；
2. 完成一个小任务，结束会话，等归档和后台提取完成（用 Helper / Studio 能看到记忆文件落盘）；
3. 换一个工具/项目，只说：`按我平时的偏好配置 lint 和测试`；
4. 对照组：临时关掉 OpenViking 再问一次，看默认风格（行宽 88、`test_*.py`）——差异一目了然。

> 💡 拿不准记忆是否在工作时，直接问 agent「检查一下 OpenViking 记忆插件的状态」，它会报告插件、服务端连接和最近的召回/捕获记录——比看截图可靠。
